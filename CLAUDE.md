# Sumchenko Works — сайт-портфолио

Статический сайт на Astro 7 + React-островки. Двуязычный: RU по умолчанию (`/`), EN под `/en/`. Деплой — статикой на VPS (см. `deploy/README.md`).

- `npm run dev` — локальный сервер, `npm run build` — сборка в `dist/`, `npm run check` — проверка типов.
- `sumchenko-works/` — исходный прототип из Claude Design (эталон вида, в сборку не входит).

## Где что лежит

- `src/content/` — **весь контент**. Код страниц для добавления проектов менять не нужно.
  - `site.yaml` — профиль, навыки, контакты, тексты схемы «Подход».
  - `taxonomy.yaml` — категории, статусы, технологии, типы артефактов.
  - `projects/<id>/project.yaml` — проект; имя папки = адрес `/works/<id>/`.
  - `projects/<id>/artifacts/` — файлы артефактов: `<artifactId>.ru.md` / `.en.md` (документы), файлы кода (`file:`), картинки/PDF.
  - `schema.ts` — схема данных (zod). Сборка падает с понятной ошибкой, если контент ей не соответствует.
- `src/lib/content.ts` — загрузка, локализация и проверка связей; `src/lib/vm.ts` — данные для компонентов.
- `src/i18n/ui.ts` — тексты интерфейса на двух языках.
- `src/components/ds/` — компоненты дизайн-системы; `src/styles/ds/` — её токены, стили и шрифты (не менять без причины).
- `src/views/` — страницы; `src/pages/` — тонкие обёртки маршрутов для RU и EN.

## Правила контента

- Текстовое поле — строка (одинаково на обоих языках) или `{ ru: ..., en: ... }`. Без `en` на английской версии показывается русский текст, а сборка выводит предупреждение со списком полей.
- Значения в инлайн-форме `{ ru: ..., en: ... }`, содержащие запятые или двоеточия, **обязательно в кавычках**: `{ ru: "Слоты, брони", en: "Slots, bookings" }`.
- Значения со спецсимволами внутри инлайн-списков (`int[]`, `user|mentor`, `0..3`, `timestamp?`) — тоже в кавычках.
- Даты вида `2025.10` — **в кавычках** (`'2025.10'`), иначе YAML превратит их в число и потеряет ноль.
- `demo: true` — проект помечается как демонстрационный; пока такие есть, на сайте видны пометки «Демо».
- `featured: true` — проект на главной (первые три по `order`). `order` — порядок в каталоге.
- `links.docs: artifacts` — кнопка «Документация» ведёт на вкладку артефактов.
- Диаграммы описываются в `diagrams:` проекта; ссылки на них (`cover`, `architecture.diagram`, `architecture.flows`, `dataModel.diagram`, `artifacts[].diagram`) — по `id` внутри того же проекта.
  - `components` — изометрическая схема: узлы с координатами `x, y` (сетка), размерами `w, d` и высотой `h`; `links` — пары id; `notes` — пояснения к узлам.
  - `erd` — сущности с полями `[имя, тип, PK|FK|UK]` и связи `[из, в, '1 : N']`.
  - `flow` — шаги `{ lane, title, text }`.
- Артефакты: `view: doc | code | erd | components | flow | image | pdf | link`. Размер и формат считаются автоматически. Для `code` подходят файлы `.yaml`, `.json`, `.sql`, `.bpmn`, `.ts`, `.go`, `.py` и др. (список — `textFiles` в `src/lib/content.ts`). Mermaid в Markdown не рисуется — схемы делать через `diagrams`.

## Разбор чужого проекта в портфолио

Когда пользователь просит перенести проект из другого репозитория:
1. Изучить репозиторий: назначение, стек, архитектуру, модель данных, API, ключевые решения.
2. Создать `src/content/projects/<id>/project.yaml` по образцу существующих (сразу RU и EN), `demo: false`.
3. Нарисовать диаграммы `components` / `erd` / `flow` по реальной структуре кода, без выдумок.
4. Вынести артефакты: требования и ADR — в `.md`, OpenAPI и схемы — как `code`-файлы.
5. Новые технологии добавить в `taxonomy.yaml`.
6. Проверить `npm run build` (ошибки схемы и связей покажутся там) и посмотреть страницу в `npm run dev`.
