## 1. Контекст

Пользователь планирует день на ноутбуке, а таймер запускает с телефона. Чтобы статистика и AI-ментор видели полную картину, данные должны совпадать на всех устройствах.

В Mito данные сначала сохраняются на устройстве, поэтому приложение работает и без интернета. Если пользователь вошёл в аккаунт, изменения отправляются на сервер, а оттуда — на другие его устройства.

Вход в аккаунт — предусловие, в этом кейсе он не описывается.

## 2. User Stories

**US-1.** Как пользователь с телефоном и ноутбуком, я хочу, чтобы изменения с одного устройства появлялись на другом, чтобы видеть актуальные задачи и план везде.

| Сценарий | Дано | Когда | Тогда |
| --- | --- | --- | --- |
| Позитивный | Я вошёл в аккаунт на двух устройствах | Создаю задачу на телефоне | Через пару секунд она появляется на ноутбуке |
| Позитивный | Задача есть на двух устройствах | Удаляю её на ноутбуке | На телефоне она тоже исчезает |
| Негативный | Одну задачу изменили на двух устройствах без интернета | Устройства подключились к сети | На обоих остаётся более поздняя правка |

**US-2.** Как пользователь, я хочу работать без интернета и не терять изменения, чтобы не зависеть от связи.

| Сценарий | Дано | Когда | Тогда |
| --- | --- | --- | --- |
| Позитивный | Нет интернета | Меняю задачи | Изменения сохраняются. Видно: «Нет сети — изменения отправятся, когда связь вернётся» |
| Позитивный | Есть неотправленные изменения | Появился интернет | Изменения отправляются автоматически |
| Негативный | Сервер вернул ошибку | Идёт отправка | Видно «Не удалось синхронизировать. Повторим автоматически.» Изменения не теряются |

**US-3.** Как пользователь, я хочу, чтобы мои данные видел только я, чтобы спокойно хранить в сервисе личные планы.

| Сценарий | Дано | Когда | Тогда |
| --- | --- | --- | --- |
| Позитивный | Есть аккаунты A и B | B запрашивает данные | B получает только свои записи |
| Негативный | На устройстве остались данные аккаунта A | Вхожу в аккаунт B | Данные A удаляются с устройства и не попадают в аккаунт B |

## 3. Use Case

| Поле | Значение |
| --- | --- |
| Название | Синхронизировать данные устройства с аккаунтом |
| Актор | Пользователь |
| Предусловие | Пользователь вошёл в аккаунт |
| Триггер | Пользователь изменил данные, открыл приложение, появился интернет или пришло изменение с другого устройства |
| Успех | Данные на устройстве и на сервере совпадают |
| Неуспех | Изменения остаются в очереди на устройстве и отправятся позже |

### Основной сценарий

1. Пользователь изменяет задачу, блок календаря или запись таймера.
2. Приложение сохраняет изменение на устройстве и добавляет его в очередь на отправку.
3. Приложение ждёт 0,8 секунды, чтобы отправить несколько правок одним запросом.
4. Приложение отправляет изменения из очереди на сервер.
5. Сервер проверяет, что пользователь вошёл и изменяет только свои записи.
6. Сервер сохраняет запись, если она новее той, что уже есть на сервере.
7. Приложение удаляет отправленные записи из очереди.
8. Приложение запрашивает изменения, появившиеся с прошлой синхронизации.
9. Приложение сохраняет у себя записи, которые новее локальных.
10. Приложение показывает статус «Синхронизировано» и время.
11. Сервер уведомляет другие устройства пользователя, и они выполняют шаги 8–10.

### Альтернативный сценарий

- **A1. Первый вход гостя.** Если пользователь работал без аккаунта, а потом вошёл, все его данные отправляются в аккаунт.

### Исключения

| Код | Ситуация | Что делает система |
| --- | --- | --- |
| E1 | Нет интернета | Не отправляет. Показывает «Нет сети» и число неотправленных изменений. Отправит, когда сеть появится |
| E2 | Ошибка сервера | Показывает «Не удалось синхронизировать». Повторяет через 2, 4, 8 … максимум 60 секунд. Очередь не очищается |
| E3 | Одну запись изменили на двух устройствах | Оставляет версию с более поздним временем изменения. Ошибку не показывает |
| E4 | Нет доступа: пользователь не вошёл или пытается изменить чужую запись | Сервер отклоняет запрос (401 или 403). Данные не меняются |
| E5 | На устройстве данные другого аккаунта | Удаляет их с устройства, не отправляя, и загружает данные нового аккаунта |

**Почему так.** Конфликт решается правилом «побеждает последняя правка», без окна выбора версии. Приложение личное, и одну задачу редко меняют на двух устройствах одновременно. Окно выбора было бы сложнее, чем сама проблема.

## 4. Процесс

Полная схема — артефакт BPMN-01, упрощённый поток — на вкладке «Архитектура».

**Почему так.** Сначала отправляем свои изменения, потом получаем чужие. Иначе приложение ненадолго показало бы старые версии поверх свежих правок пользователя.

## 5. API

Отдельного сервера для синхронизации нет: используется готовый REST API Supabase. В каждом запросе передаётся токен пользователя, по нему сервер понимает, кто пришёл.

| Метод | Путь | Что делает | Ответы |
| --- | --- | --- | --- |
| POST | `/rest/v1/rpc/push_records` | Отправить пачку изменений (до 200 записей) | 200 — принято; 400 — неверные данные; 401 — не вошёл; 403 — чужая запись |
| GET | `/rest/v1/records?rev=gt.{N}` | Получить записи, изменённые после последней синхронизации (до 500) | 200 — список записей; 401 — не вошёл |

Пример тела запроса `push_records`:

```json
{
  "changes": [
    {
      "id": "0192a3b4-5c6d-7e8f-9a0b-1c2d3e4f5a6b",
      "collection": "tasks",
      "updatedAt": 1759140000000,
      "deletedAt": null,
      "doc": { "id": "0192a3b4-5c6d-7e8f-9a0b-1c2d3e4f5a6b", "title": "Разобрать главу 3", "status": "open" }
    }
  ]
}
```

## 6. Модель данных

Все сущности (задачи, блоки, записи таймера) хранятся на сервере в одной таблице `records`. Подробно — в словаре данных DD-01 и на схеме ERD-01.

**Почему так.** Запись не удаляется из базы, а получает отметку `deleted_at`. Если бы строка исчезла, устройство, которое было офлайн, никогда бы не узнало, что её удалили.

## 7. Задача на разработку

**MITO-7. Синхронизация данных между устройствами**

**Цель.** Пользователь с аккаунтом видит одинаковые данные на всех устройствах и может работать без интернета.

Что сделать:

1. Таблица `records` в Supabase: пользователь видит и меняет только свои строки.
2. Функция `push_records`: сохраняет запись, только если она новее серверной.
3. Очередь неотправленных изменений на устройстве.
4. Синхронизация: через 0,8 с после правки, при открытии приложения, при появлении сети, по кнопке.
5. Статус в интерфейсе: «Синхронизировано», «Нет сети», «Ошибка».

**Критерии приёмки:** все сценарии из раздела 2.

Нефункциональные требования:

- Безопасность: пользователь видит только свои данные (правило доступа в базе).
- Надёжность: изменения, сделанные без сети, не теряются. После ошибки — автоматический повтор.
- Удаление — только отметкой `deleted_at`.

## 8. Замечания аналитика

При сверке с кодом я нашёл места, которые стоит доработать.

| # | Что нашёл | Чем грозит | Что предлагаю |
| --- | --- | --- | --- |
| 1 | Если два устройства изменили запись в одну и ту же миллисекунду, каждое оставляет свою версию | Устройства навсегда расходятся (редкий случай) | Добавить второе правило сравнения на случай равного времени |
| 2 | «Более поздняя правка» определяется по часам устройства | Если часы телефона спешат, его правки побеждают даже более новые | Для личного приложения допустимо. Иначе — брать время сервера |
| 3 | Таймер можно запустить на двух устройствах | После синхронизации появляются две записи времени на один и тот же промежуток | Проверять пересечения после синхронизации |
| 4 | Удалённые записи остаются в базе навсегда | Таблица растёт, новое устройство скачивает и удалённое | Удалять старые отметки об удалении |
