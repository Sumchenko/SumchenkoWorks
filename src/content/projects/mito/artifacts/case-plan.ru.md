## 1. Контекст

Расставлять задачи по часам — отдельная работа, и именно на ней люди бросают планирование. В Mito это можно поручить AI-ментору. Он учитывает сроки, приоритеты, уже занятое время в календаре и привычный ритм пользователя, а затем предлагает расписание на сегодня или завтра.

Ничего не попадает в календарь без подтверждения: пользователь смотрит предложенный план и сам выбирает, что добавить. Функция доступна и без аккаунта.

## 2. User Stories

**US-1.** Как пользователь, которому трудно планировать, я хочу получить план дня одной кнопкой, чтобы не тратить силы на расстановку задач.

| Сценарий | Дано | Когда | Тогда |
| --- | --- | --- | --- |
| Позитивный | Есть открытые задачи и свободное время | Нажимаю «Составить план» | Вижу список блоков: время, задача, почему в это время. Календарь пока не изменён |
| Негативный | Нет подходящих задач или свободного времени | Нажимаю «Составить план» | «Свободного времени или подходящих задач нет — план не нужен.» |
| Негативный | AI-модели недоступны | Нажимаю «Составить план» | «Ментор временно недоступен. Попробуйте позже.» |

**US-2.** Как пользователь, я хочу сам выбрать, какие блоки добавить в календарь, чтобы план оставался моим.

| Сценарий | Дано | Когда | Тогда |
| --- | --- | --- | --- |
| Позитивный | Показан план из 5 блоков | Снимаю отметку с двух и нажимаю «Добавить в календарь (3)» | В календаре 3 новых блока. Задачам проставлен день выполнения |
| Негативный | Пока я смотрел план, одну задачу удалили | Нажимаю «Добавить» | Блок удалённой задачи пропускается, остальные добавляются |

**US-3.** Как пользователь, я хочу написать пожелание («после 15:00 встреча»), чтобы план подходил под мой день.

| Сценарий | Дано | Когда | Тогда |
| --- | --- | --- | --- |
| Позитивный | Ввёл пожелание | Нажимаю «Составить план» | Пожелание учитывается в плане |
| Негативный | Сделал слишком много запросов подряд | Нажимаю «Составить план» | «Лимит запросов исчерпан. Попробуйте через N мин.» |

## 3. Use Case

| Поле | Значение |
| --- | --- |
| Название | Составить план дня с помощью AI |
| Актор | Пользователь (гость или с аккаунтом) |
| Предусловие | В приложении есть задачи |
| Триггер | Кнопка «Составить план» |
| Успех | Выбранные пользователем блоки добавлены в календарь |
| Неуспех | Календарь не изменён, пользователь видит причину |

### Основной сценарий

1. Пользователь выбирает «Сегодня» или «Завтра», при желании пишет пожелание и нажимает «Составить план».
2. Приложение собирает данные: открытые задачи, календарь на 4 дня, статистику за 2 недели.
3. Приложение отправляет данные на сервер ментора.
4. Сервер проверяет запрос и лимит: не больше 10 запросов в минуту и 60 в сутки с одного адреса.
5. Сервер отправляет данные AI-модели и просит составить план.
6. Сервер проверяет ответ модели: убирает блоки с неправильным временем и с задачами, которых нет у пользователя.
7. Приложение показывает план. Все блоки отмечены.
8. Пользователь снимает отметки с ненужных блоков и нажимает «Добавить в календарь».
9. Приложение создаёт блоки в календаре и проставляет задачам день выполнения.
10. Приложение показывает «Добавлено в календарь: N».

### Альтернативные сценарии

- **A1. Другой вариант.** На шаге 7 пользователь нажимает «Другой вариант» — сценарий повторяется с шага 2.
- **A2. Модель не ответила.** На шаге 5 модель вернула ошибку или неправильный ответ — сервер спрашивает следующую модель: Groq → Gemini.

### Исключения

| Код | Ситуация | Ответ сервера | Что видит пользователь |
| --- | --- | --- | --- |
| E1 | Неправильный запрос (например, пожелание длиннее 500 символов) | 400 | «Не удалось отправить запрос.» |
| E2 | Превышен лимит запросов | 429 | «Лимит запросов исчерпан. Попробуйте через N мин.» |
| E3 | Все модели недоступны или сервер занят | 503 | «Ментор временно недоступен. Попробуйте позже.» Запрос не списывается с лимита |
| E4 | Модель предложила задачу, которой нет у пользователя | 200 | Этого блока нет в плане: сервер его убрал |
| E5 | Задачу удалили, пока пользователь смотрел план | — | Блок не добавляется, остальные добавляются |

**Почему так.** План сначала показывается, и только потом добавляется. Модель может ошибиться, а календарь — личное пространство. Лишний клик дешевле, чем потерянное доверие к сервису.

## 4. Процесс

Полная схема — артефакт BPMN-02, упрощённый поток — на вкладке «Архитектура».

**Почему так.** Ответ AI-модели проверяет сервер, а не сама модель. Модель может придумать задачу или время, поэтому её ответу нельзя доверять без проверки.

## 5. API

| Метод | Путь | Что делает | Ответы |
| --- | --- | --- | --- |
| POST | `/api/mentor` | Получить план дня | 200 — план; 400 — неправильный запрос; 429 — лимит; 503 — модели недоступны или сервер занят |

Авторизации нет: функция доступна гостям. Защита — лимит запросов по адресу.

Пример запроса (сокращённо):

```json
{
  "mode": "plan",
  "lang": "ru",
  "date": "2026-09-29",
  "note": "после 15:00 встреча",
  "context": {
    "now": "2026-09-29T10:05",
    "tasks": [
      { "ref": "t1", "title": "Разобрать главу 3", "priority": 2, "estimateMin": 60, "dueDate": "2026-09-30" }
    ],
    "blocks": [
      { "ref": "b1", "date": "2026-09-29", "start": "11:00", "end": "12:00", "title": "Созвон" }
    ]
  }
}
```

Пример ответа:

```json
{
  "summary": "Глава 3 — после созвона, срок завтра.",
  "blocks": [
    { "taskRef": "t1", "date": "2026-09-29", "start": "12:15", "end": "13:30", "reason": "срок завтра" }
  ]
}
```

Модель видит задачи под короткими ссылками `t1`, `t2`, а не под настоящими идентификаторами. Какая ссылка к какой задаче относится, знает только приложение.

## 6. Модель данных

`TASK` и `TIME_BLOCK` хранятся на устройстве пользователя, `DAILY_LIMIT` — таблица на сервере ментора, считает запросы за сутки. Подробно — в словаре данных DD-02.

**Почему так.** Адрес пользователя хранится только в виде хеша — необратимого преобразования, по которому адрес не восстановить. Для лимита достаточно отличать пользователей друг от друга, а сам адрес — лишние персональные данные.

## 7. Задача на разработку

**MITO-8. План дня от AI-ментора**

**Цель.** Пользователь одной кнопкой получает план дня и сам решает, что добавить в календарь.

Что сделать:

1. Кнопка «Составить план» с выбором «Сегодня» / «Завтра» и полем пожелания.
2. Сбор данных для модели: задачи, календарь, статистика за 2 недели.
3. Сервер ментора `POST /api/mentor`: проверка запроса, лимит, запрос к модели, проверка ответа.
4. Если модель не ответила — запрос к следующей.
5. Показ плана с отметками и кнопка «Добавить в календарь».
6. Блоки ментора помечаются `origin = mentor`.

**Критерии приёмки:** все сценарии из раздела 2.

Нефункциональные требования:

- Безопасность: ключи AI-моделей хранятся только на сервере. Адреса пользователей — только в виде хеша.
- Проверка данных: сервер отклоняет неправильные запросы и убирает неправильные блоки из ответа модели.
- Логирование: сервер записывает, какая модель ответила и за сколько времени.

## 8. Замечания аналитика

| # | Что нашёл | Чем грозит | Что предлагаю |
| --- | --- | --- | --- |
| 1 | Поле пожелания в интерфейсе не ограничено, а сервер принимает не больше 500 символов | Длинное пожелание даёт непонятную ошибку «Не удалось отправить запрос» | Ограничить поле 500 символами и показывать счётчик |
| 2 | Правила «не ставить блок в прошлое» и «не пересекать существующие блоки» есть только в тексте запроса к модели. Сервер их не проверяет | Модель может нарушить правило, и такой блок попадёт в календарь | Добавить эти проверки на сервер |
| 3 | Лимит считается по адресу, а не по пользователю | Люди в одной сети (офис, общежитие) делят один лимит | Для пользователей с аккаунтом считать лимит по аккаунту |
| 4 | Нет общего ограничения времени ожидания | Если модели отвечают медленно, пользователь ждёт несколько минут | Ограничить ожидание, например, одной минутой |
