Рабочий план проекта: цель, ограничения окружения, этапы и что проверено на каждом. Ведётся в репозитории вместе с кодом и обновляется после каждого значимого шага.

## Цель

Ссылки на пет-проекты получают работодатели. Нужен сервис, который непрерывно проверяет, что проекты **живы и полностью рабочие**, и сразу сообщает о падении — до того, как работодатель откроет неработающую ссылку.

В итоге должно быть:

- обзор «всё зелёное / что-то упало» — в Grafana и в простом веб-интерфейсе;
- добавление, удаление и отключение проектов без пересборки;
- графики: текущий статус, аптайм, время ответа, история падений, ошибки;
- уведомления о падении и восстановлении в Telegram;
- работа 24/7 на VPS.

## Ограничения окружения

| Что | Следствие для требований |
| --- | --- |
| Чекер будет жить на том же VPS, что и проекты | Если VPS упадёт, чекер упадёт вместе с ними и никого не предупредит — внешний мониторинг самого чекера обязателен |
| Один проект использует бесплатный Supabase, который засыпает после ~7 дней без запросов | Регулярные проверки должны обращаться к базе; для REST API Supabase нужен заголовок `apikey` — у целей есть свои заголовки |
| Будущие проекты — на бесплатных хостингах с холодным стартом 30–60 с | Настраиваемый таймаут на цель и проверки чаще, чем хостинг засыпает |
| В проектах пока нет `/health`-эндпоинтов | Проверяем главную страницу и ключевое слово на ней |

## Этапы

| Этап | Содержание | Состояние |
| --- | --- | --- |
| 0. Подготовка | Аудит первой версии — 10 проблем; план; ответы владельца на вопросы | Готово |
| 1. Ядро | Логика «жив / не жив» (2xx = UP), один таймаут на проверку, вычитывание тела, свои миграции, корректная остановка, pgx, slog, тесты | Готово |
| 2. Цели в БД | Таблица `targets`, свои интервал, таймаут и код, ключевое слово, заголовки, подхват изменений без рестарта | Готово |
| 3. Интерфейс и API | Веб-интерфейс, JSON API, валидация, немедленное применение изменений, Basic Auth, защита от CSRF, `/healthz` | Готово |
| 4. Grafana как код | Datasource и дашборд из репозитория, read-only пользователь, панели аптайма, времени ответа, ошибок, срока SSL | Впереди |
| 5. Уведомления | DOWN после N неудачных проверок подряд, RECOVERED при восстановлении, без спама; истечение SSL | Впереди |
| 6. Качество | Тесты обработчика и API; CI с `go vet`, `-race`, линтером и сборкой образа | Впереди |
| 7. Продакшен | Секреты в `.env`, non-root контейнер, защита от перебора пароля, деплой за Caddy с HTTPS, очистка старых данных и бэкап, внешний мониторинг чекера | Впереди |

## Как проверялся каждый этап

- **Этап 1.** `go vet`, `go test -race` по всем пакетам; интеграционные тесты хранилища на PostgreSQL 15 — и на чистой базе, и на базе первой версии со старыми данными; запуск в Docker и `docker stop` с кодом выхода 0. Keep-alive работает: время ответа GitHub 916 → 189 мс со второй проверки.
- **Этап 2.** Тесты планировщика 30 раз подряд без флейков; перенос старой истории; сквозной прогон в Docker: добавление, выключение и изменение целей подхватываются за 3 с и быстрее, ключевое слово отличает рабочую страницу от нерабочей.
- **Этап 3.** Тесты веб-слоя на фейковом хранилище: авторизация, CSRF, формы, API, валидация; сквозной прогон: `/healthz` 200 без пароля, интерфейс 401 без пароля, создание через API 201, форма с ошибкой 422, межсайтовый POST 403, статус контейнера healthy.

## Известные проблемы

1. Дашборд Grafana существует только внутри контейнера и сломан переименованием колонок — переделывается на этапе 4.
2. Пароли захардкожены в compose, Postgres открыт наружу, образы `:latest`, контейнер от root — этап 7.
3. Нет очистки старых проверок — этап 7.
4. В CI нет `vet`, `-race` и линтера — этап 6.
